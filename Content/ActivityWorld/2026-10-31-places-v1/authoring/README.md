# 咕游记相遇故事改写说明

玩家在城市地点页选一个真实地点，点「去这里逛逛」。人物已经因为自己的事情到了那里。写清楚那个人为什么此时此地会与玩家短暂搭上话，以及玩家的两次选择怎样改变这次相遇。这批任务覆盖当前发布版的 200 位城市相遇角色。Oliver、Ruby、Marcus 的首次结识属于主线旅伴流程。

## 给网页版 AI 的指令

可以把本说明、`story-template.json` 和所选城市的角色卡一起上传。用姓名或 `npcId` 点名，每次先写同一地点的 1–3 位，便于读完四条路径，也能和同场其他人物一起做情节去重。

> 根据上传的角色卡和地点事实，重写我点名角色的双语初遇与重逢。每人交一份符合 `story-template.json` 的 JSON 对象，文件名为 `<npcId>.json`。只使用点名角色的固定资料和当前唯一地点。保留对应的 `id`、`npcId`、`placeId` 和七节点结构。为这一次相遇重新设计到场动机、当下状态和两次互动。按四条完整路线逐条读完，再核对重逢是否适用于所有旧识。正文、选项和重逢写中英双语，因果说明写中文。每篇以 `reviewStatus: "draft"`、`reviewEvidence: []` 交稿。

## 角色卡和地点怎么用

- **固定资料**采用发布版的 `assignment.card`。身份、年龄、外貌、职业、核心性格、兴趣、价值观、缺点、说话习惯、边界、国籍、成长地、现居城市、唯一相遇地点和头像都按现有绑定。旧的迁居经历保留在人物传记里。
- **本次情境**可以另写。角色可以喜欢、讨厌或对这个地方没感觉，也可以因工作、等人、还东西、照看家人或临时改道出现在这里。长期性格与当下状态可以不同。社交能力强的人今天也可能忙、疲惫或戒备。
- **空间**以城市资料里列出的实拍和 `spaceFacts` 为边界。临时随身物件可以出现，前提是人物确实有理由带来。把接触发生的位置、人物动线和物件去向写实。避免编造能解围的地标或设施、现场票价、班表、开放时间和许可。
- **现稿参考**里的地点适配和旧剧情标题帮助理解已有版本。新稿可以替换现稿的当天理由、触发和结果。确需改人物设定或换地点时，另列建议供人工决策。

## 玩家实际怎么读

点进地点后，正式活动根据该地点的候选角色和账号相遇历史进入初遇、重逢或独处。教程给每处安排一个固定的初遇用于练习。初遇用「继续」逐段揭示内容，在当前节点末尾出现两项选择。点其中一项后进入对应节点，已读内容和选过的回答仍留在阅读页。到叶子读完，用户可结束这次外出。完成后界面可出现加好友或继续聊天，好友关系由系统另行处理。

开场和分支是预写内容。选项由玩家点选，推进时由系统按 `next` 读取下一节点。英文正文可点词，用户可打开中文对照和自动朗读。重逢只顺序阅读一段完整的小情境。独处使用地点已有的中英文案，随地点资源维护。

```text
start
├── 选项 1 → a
│   ├── 选项 1 → aa（结束）
│   └── 选项 2 → ab（结束）
└── 选项 2 → b
    ├── 选项 1 → ba（结束）
    └── 选项 2 → bb（结束）
```

每人交 **7 个初遇节点、6 个选项、4 个实际结局、1 段重逢**。每位玩家走 3 个初遇节点，作 2 次选择。节点顺序可以按模板排列，`choices` 的数组顺序由校验器锁定。四个叶子都用 `"choices": []`。

## 交稿字段

| 字段 | 填写规则 |
| --- | --- |
| `id` | 城市角色卡给出的故事 ID，即 `storyId` |
| `npcId` | 角色 UUID，从城市角色卡原样复制 |
| `placeId` | 唯一相遇地点 ID，从城市角色卡原样复制 |
| `titleZh` | 初遇中文标题，1–80 字符 |
| `nodes` | 7 个对象，每个有 `id`、`beats`、`choices` |
| `beats[]` | 每段有 `speaker`、`english`、`chinese`。说话人只能为 `narrator` 或 `npc`。英文 1–420 字符，中文 1–260 字符 |
| `choices[]` | 每项有 `english`、`chinese`、`next`。英文 1–180 字符，中文 1–100 字符。按上图给出下一节点 |
| `reunion` | `titleZh` 和 `beats`。标题 1–80 字符，用同一段落格式，共 4–6 段。首段是旁白，至少两段是 NPC 台词 |
| `causality` | 附下表的十项中文说明。每项 1–4000 字符，写到能逐条核对即可 |
| `reviewStatus` | 初稿固定 `"draft"` |
| `reviewEvidence` | 初稿固定 `[]`，审校完成后由发布流程填写 |

每个初遇节点 **4–6 段**，至少 1 段旁白、2 段 NPC 台词，`start` 首段必须是旁白。当前在用的 200 篇初遇和重逢均采用 4 段。模板按「旁白、NPC、旁白、NPC」给出四段，其他符合条件的排列也通过当前运行时校验。角色动作写进旁白，NPC 台词只写实际说出口的话，免加角色名、引号和动作括注。玩家的台词和动作写在选项里。

交稿对象的键按模板原样使用。角色卡、地点、独处正文、好友、奖励及联网进度均由各自的内容或运行接口管理。请只输出故事对象，JSON 中无注释及额外字段。

| `causality` 字段 | 说明 |
| --- | --- |
| `presenceReason` | 玩家出现前，NPC 已经为什么来到这里 |
| `placeAttitude` | NPC 怎么看待这处地方，有何在场感受 |
| `stayingConstraint` | 为什么暂时还在这里，何时有理由离开 |
| `currentGoal` | 当下自己想完成或避免什么 |
| `currentState` | 当天的精力、情绪、警惕程度或注意力如何，怎样看得出来 |
| `contactTrigger` | 哪个可观察细节让两人有理由搭话，谁先开口 |
| `characterContinuity` | 哪些动作为这个人物独有，如何体现原卡的习惯、缺点或边界 |
| `reactionAndChange` | 分别写明 `aa`、`ab`、`ba`、`bb` 接住了什么选择，最后具体发生了什么 |
| `spatialContinuity` | 位置、朝向、时间和关键物件在分支中的去向 |
| `reunionCommonFacts` | 这次重逢借用了哪些所有旧识都成立的事实，什么由当天情境重新交代 |

## 创作和自检

1. **让事情先发生。** 开场交代可见的地点、角色已经在做的事、具体的接触缘由。比如 Elliot 本来在复走南岸的一段步道，碰到有人经过才需要停下来。玩家询问他为什么来回走和把空间让给他，应当换来两种不同的下一步。
2. **选项是承诺，下一段要兑现。** 把玩家刚选的动作或话接上，再让人物用自己的方式回应。顺着四条完整路线核对人在哪里、东西在谁手里、已经说过哪句话。玩家的名字、年龄、能力、消费意愿和过去经历保持开放。
3. **给四个结尾各自的结果。** 有人可以继续聊，也有人照旧做完自己的事、改主意、误会没有完全消除，或礼貌分开。让分歧落在行动、边界和关系距离上。避免全是「配合就赢，拒绝就输」或同一个顿悟换四种说法。每个叶子都收束眼前的交流。
4. **重逢从今天开始。** 所有路径和早期旧活动都可能让玩家与此人相识。可写认出对方，然后交代新的当下情境。先前的回答、物件、承诺、消费、帮忙和私人话题，只有确定为共同事实才可引用。遇到分支专属细节，改为今天重新发生的事。
5. **给同城的人不同的日子。** 同地批次对照到场理由、谁开口、触发事件、物件、互动结构、情绪转折、结尾和重逢情节。留意反复出现的掉东西、让座、帮选颜色、请陌生人评判工作、职业课和微小善意说教。保留情绪温差与含混，日常里可以有热络、烦躁、尴尬、得意和不耐烦。人物可以因为今天的处境显得反常。英文读出声要像现在的日常口语，中文译文对齐同一动作、语气和事实，避免古雅书面措辞、格言式总结和流水账。

## 接入时要对齐的接口

创作者使用上面的 JSON 合同。以下是项目维护者核稿和集成时用的边界。

- 发布源中每个角色的 `assignment.storyId` 指向同一条故事记录。故事的 `id`、`npcId`、`placeId` 三者和现有绑定完全吻合。发布给手机的 `BackendOuting.story` 只带 `id`、`titleZh`、`nodes`、`reunion`。`causality` 和审核资料留在内容源。
- 切换分支用的选项编号来自当前节点和零基数组位置。第一项是 `start:0`，第二项是 `start:1`，下一层同理。稿件里只填写 `next`。`runId`、读到哪段的 `beatIndex`、所选 `choices`、`revision` 和状态由系统产生。
- 本包的模板直接对应发布内容源的 `placeEncounterStorySchema`。旧创作脚本里还有 `scenes`、`firstChoice`、`secondChoice` 格式，那是旧脚本转换输入。此批交稿直接按模板使用 `nodes`、`beats`、`choices` 和 `next`。

| 运行接口 | 用途与主要字段 |
| --- | --- |
| `GET /v2/activity-world?releaseId=…` | 取当前城市地点目录 |
| `POST /v2/outings` | 按 `runId`、`releaseId` 和 `placeId` 建立相遇或独处会话 |
| `GET /v2/outings/active`、`GET /v2/outings/:runId` | 取活跃会话和指定会话快照 |
| `GET /v2/outings/history?before=…` | 分页读取历史 |
| `POST /v2/outings/:runId/read` | 通过 `operationId`、`expectedRevision`、`beatIndex` 记录阅读进度 |
| `POST /v2/outings/:runId/presented` | 开场可见并读到节点末尾后确认已呈现，独处正文显示后也走此操作 |
| `POST /v2/outings/:runId/choices` | 用 `operationId`、`expectedRevision`、`choiceId` 提交一次点选 |
| `POST /v2/outings/:runId/complete`、`/abandon` | 结束或主动提前离开，提交 `operationId` 和 `expectedRevision` |

回收稿件后，先按 UUID 与绑定合并到草稿，再用后端 `placeEncounterStorySchema` 和世界校验器验证。做完逐人四路复核和同地点横向复核，再产生新版本的审校指纹、后端发布包与配套 App 清单。现有发布、历史记录和头像绑定作为基线留存。

主要合同来源位于仓库的 `Backend/src/modules/npc/activity-world-content.ts`、`authored-content.ts`、`outing-routes.ts` 和 `Packages/LingoKit/Sources/DomainKit/World/PlaceOutingProgress.swift`。
