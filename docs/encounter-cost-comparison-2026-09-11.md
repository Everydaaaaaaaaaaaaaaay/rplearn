# 相遇请求合并费用实测 · 2026-09-11

结论：没有观察到省钱。在可完整完成的诊断组中，合并方案平均 ¥0.00260334，逐轮方案 ¥0.00245862，合并贵 5.89%（约 0.145 积分/次）。样本每方案仅 2 次，不能据此认定长期差异；更合适的产品结论是费用基本接近、交互等待减少。

## 方法与边界

用户明确授权简单真实费用测试。使用原生 `SocialDialogueService.reply` 与 `plan`，同一虚构 Dev Singh 角色卡、伦敦公园喝咖啡场景、junior3、空历史。逐轮走观景→邀请保持联系；合并生成完整分支。人物生成在两种方案中相同且独立，未重复收费测试。

原生测试通过 loopback SSH bridge 调用线上相同版本的 OpenRouter provider client。schema 前缀序列化与 BackendLLMProvider 相同；服务端读取当前 character_generation 路由：GLM 5.3 Flash、温度 0.7、上限 2400、60 秒。固定同一实验 userReference，不混入真人聊天。使用真实 usage.providerCostUsd × 7.2，不把 token 推算值当账单。

这是原生服务→真实供应商的小样本，不经过生产用户账户或积分结算，无生产用户数据/额度写入。供应商真实费用仍产生。没有更改生产路由、模型、套餐或客户端逻辑。每条调用保存原始请求、响应、usage 和耗时；所有调用缓存命中均为 0。未做供应商 provider 固定，不能排除底层路由与采样波动。

## 第二组：诊断对照（非线上配置）

两种方案都仅在实验桥上使用 reasoning.effort=minimal；旧版预算由 260 放宽到 512，实际没有用满（各次 61–80 输出 tokens），新版预算仍 2400。除此以外保留各自现有请求和服务校验。按 old1/new1/new2/old2 顺序执行，4 次相遇均完整成功。

| 指标（每次完整相遇均值） | 逐轮请求 | 一次完整分支 |

建议保留预生成带来的连续交互体验，但不宣传为明确省钱；下一项优先处理相遇的思考开销与完整输出可靠性。此轮只测量，尚未自动把诊断配置用于生产或改动角色生成策略。
