# 首批公共补库失败案例

日期：2026-09-26。角色 Oliver，档位小学三年级。运行证据在服务端 `learning_generation_runs`，任务 `c76014ca-6e3c-455d-ad9f-4fa018b9171a`；仅使用公开课程资料，没有私人聊天。三次尝试均未发布，不可算作新增预设或已验收课程。

## 第一次：审核协议未完成，另有内容缺陷

作者返回正常 JSON；独立审核用满 9000 输出 token，未形成可验证报告。不能据此宣称审题模型发现了语义错误。已显式关闭供应商推理输出，给结构化审题保留输出空间；后续调用分别为 2111、1884、827 输出 token，没有再耗尽预算。

作者候选另有这些问题，由本任务编写者逐题核读发现：

- 没有图片，提示却说“看图旁的英语名字”。现已加入文字题的缺图指代硬性拒绝。
- 解释把 `I am like…` 泛化为多余 be 动词。这个形式可以表示“我像……”，本题应该说明它不表达“喜欢”，不能把不同语义的合法句型一概判成语法错误。
- 解释说 `this` 不能放句首，缺少“本题所需词序”的限定。生成规范现明确要求限定语境，不写此类错误总规则。

## 第二次：作者合同与提示矛盾

作者输出中混入 dictation 和未提供的音频资产，还增加了 `referenceLimitations` 顶层字段。严格解析拦住了输出，未进入审题阶段。程序发给作者的 Schema 当时仍包含六种题型，与文字补库白名单矛盾。

规范第 3 版的 Schema 仅包含 choice、arrange、completion、matching；明确六个顶层字段。测试检查供应商实际收到的 Schema，不仅检查程序事后的拒绝。没有通过忽略多余字段、虚构音频或降低资料要求来放行。

## 第三次：报告有效不等于审核可靠

作者合同通过，主目标覆盖检查通过；独立审题形成了结构完整的报告，但仍未达到发布条件。

- 配对题解答用了 `father → 爸爸` 等文字，合同要求 `l1 → r1` 等稳定标识。确定性判题拒绝这种报告。后续应改进每题专属答案合同和示例，不跳过答案核对。
- 审题报告把“请填写 people 的正确形式”直接说成语法错误。实际上正确形式可以保持不变，不能因为不需变形就认定语法错误；这说明模型会产生错误的拒绝理由。
- 该题把 `people` 直接给在指令和提示中，对家庭称呼目标的测量很弱，并引入不规则复数；应重写题目及目标映射，而不是用模型的错误语法理由作为教研结论。
- 介绍人物题的提示过于接近选项中的关键形式，目标范围和提示辅助程度仍需逐题复核。剧情和题目必须一起检查，不能只凭模型的 `true` 字段判断无泄题。

## 下一步要求

实现可追溯的编辑修订→重新独立审题→最终逐题批准流程。首批编辑不得直接把失败报告改成通过；保留原稿、修订差异、实际编辑者、新哈希与重新审题证据。独立审题要使用本题的标识枚举，降低“理解正确、协议错误”的浪费；内容拒绝理由需由编辑复核。
