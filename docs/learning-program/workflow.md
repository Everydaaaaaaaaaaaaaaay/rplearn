# 执行工作流、模板与自我纠错

与 [总方案](README.md) 一起使用。用户已于 2026-09-16 启动工程，按以下流程执行。

正式工作流版本：`WF-1.3`；生效版本与修订记录见 [工作流版本账本](workflow-versions.md)。工程已启动；采用记录不代表长期运行效果已获验证。

## 1. 每次开始工作的固定步骤

1. 读取 [工作流版本账本](workflow-versions.md)，确认生效版本，再读取本工作流、[进度账本](status.md)、当前批次卡和相关上轮结果；核对当前 Git 状态，不重做已完成且仍适用的工作。
2. 选择一个有明确终点的目标，例如“核实三档自评后的复习反馈”“实现离线评分幂等”，不是“继续优化学习系统”。
3. 列出本轮输入、交付物、接受/否决条件和未知；只读取相关代码及证据。
4. 确认工作在已授权范围内；2026-09-16 已获工程启动授权，后续实施仍须先通过证据与设计门槛。
5. 优先补最影响决策的不确定性；不要因为容易就连续做装饰性功能。

## 2. 一轮标准循环

### 发现与核实

- 以手机 App 为主要研究对象；官网、商店页和论文用于补证。分别标记原生 App 实操、官方移动端截图、官方文档、网页实操，禁止跨平台升级证据。移动端深研队列优先于纯网站扩展。

- 必须实际联网搜索并打开来源：优先官网、官方帮助、当前演示、算法原始文档及学习研究；结合实操与独立反馈。模型知识只用于提问，不能当证据。记录检索词、原始 URL、访问时间和支持的具体论断；搜索摘要不算已阅读。
- 使用固定任务比较：新用户开始、遇到不懂的内容、错误反馈、复习完成、查看统计、离线中断后恢复。
- 一个核心机制至少记录初始、操作、结果三个状态；复杂反馈补充错误与退出状态。字幕同步和连续播放用视频证据，不能用静态图声称通过。
- 文件名包含研究 ID、产品、平台、日期、步骤；隐去真实账号和私人内容，不将凭证写进研究仓库。
- 记录版本、来源 URL、进入路径和不可访问部分。证据过时或所处平台不同要复核，不能把 Android 行为直接当作 iOS 事实。

### 抽象与反驳

- 把功能翻译成“用户困难—学习机制—交互动作—预期结果”，不要只写“做一个某某同款”。
- 为候选方案写至少一个替代方案和“什么都不改”的对照。
- 主动寻找不适合我们的证据：增加操作负担、抢走聊天注意力、内容成本过高、虚假掌握感、已有功能足够。
- 明确最危险假设以及最便宜的验证方式；先测该假设，再写大段生产代码。

### 原型与实施

- 比较现有入口、新页面、新 Tab、独立学习系统的适配性，选择最能完成学习任务的方案；不强行复用布局。保留已有聊天等优秀能力，按需复用组件；原型使用代表性长短内容，不能只看一个理想长度的卡片。
- 先验证用户能否理解“何时翻答案、如何评分、下一步去哪”，再精修视觉。与现有照片背景、玻璃材质、排版保持协调，但优先确保训练时的专注和可读性。
- 开发前完成数据口径、迁移/同步、离线、成本、权利、验收定义；涉及多个模块时写边界，避免 Feature 互相依赖。
- 优先做一个可用的纵向切片：来源 → 练习 → 结果 → 下一次安排 → 统计，不先造庞大通用框架。
- 可用特性开关隔离新功能；失败关闭时保持已有收藏、聊天和学习历史可读。回退不得靠删库。

### 验证与纠错

- 运行测试前核对当前工具链路径与目标包含的测试文件；零用例不算通过。不要沿用失效的机器路径，也不要为文档改动重建 App。
- 若编译报接口不存在而源码已声明，先确认新源文件进入编译清单，并比较产品模块与中间模块的生成时间；有旧模块遮蔽证据时，只移动对应生成缓存并重跑受影响测试。没有证据不清缓存，不删除用户数据或整份构建目录。

- 先按预先定义的案例验证，不因结果不理想临时改口径。
- 若失败，区分：实现错误、内容错误、交互误解、教学机制无效、研究证据误判、样本不足。
- 实现/内容错误：补能抓住问题的测试或审核规则，修复，再重测受影响路径。
- 用户误解：调整交互，再让未看过原型的人试，避免把解释后的熟练当成自然可用。
- 教学机制无效：允许改设计或放弃；不能靠增加奖励、延长时长掩盖学习成绩没改善。
- 证据误判：更正原研究卡及所有引用它的决策，写明版本和影响范围，不静默覆盖历史。
- 样本不足：保留“待验证”，不能将未发现问题改写为已证明有效。
- 每次修正记录“触发证据 → 原因 → 调整 → 重验结果 → 剩余限制”。

### 提交与交接

- 每个完成且验证过的逻辑改动做聚焦提交，显式暂存文件，检查 staged diff；不提交账号、缓存、凭证、大量临时截图和构建产物。
- 研究整理、算法/数据、界面集成、统计、后端与修复可以分次提交，但每次都要说明独立结果，不用任意数量的提交衡量进度。
- iOS 改动后按仓库要求安装最新模拟器预览；后台部署与 iOS 分发分别记录。仅文档工作不做无意义的 App 构建。
- 更新账本：完成/未完成、证据、提交、阻塞、下一项具体动作。面向用户说明收益、验证与限制，不只汇报改了多少文件。

## 6. 自查门槛

### 研究完成前

- [ ] 已实际联网检索并阅读权威来源，内部流程有画面证据；关键论断逐条可追溯，访问日期/平台明确。
- [ ] 区分观察、官方宣称、用户反馈和推测，没有“没看过但默认有”。
- [ ] 覆盖成功、失败、退出与恢复，不只展示首页。
- [ ] 比较过替代方案，指出至少一项不应照搬的设计。
- [ ] 学习价值不是以界面漂亮或竞品知名度代替。

### 开发前

- [ ] 能说明目标人群、学习问题、成功/失败证据。
- [ ] 与聊天整合自然，训练频率可控，旧功能和非训练用户不受迫使。
- [ ] 数据口径、词义/来源、算法映射、版权、成本、离线与回退已定义。
- [ ] 没有把 AI 当成确定性计数器、调度器或每次翻卡的必需依赖。
- [ ] 验收方式能抓住真实错误，而不是只验证“按钮存在”。

### 标记完成前

- [ ] 核心用户任务走通，统计能与原始事件核对。
- [ ] 长文本、空数据、已有用户、低端设备和错误状态经过适当检查。
- [ ] 多端与离线不会重复记账；账号和私人聊天数据不泄露。
- [ ] 记录成本、延迟、已知问题和未测设备，不把模拟器等同真机。
- [ ] 实现可用、用户可用、学习效果已证实三个状态分开写。
- [ ] 提交和部署范围明确，延期观察指标仍留在账本。

任何关键项不满足，该项保持“验证中/待补证”，不能通过措辞变成完成。重复失败两轮后重新检查假设；三轮仍不能解释收益时暂停该候选，转做其他独立工作，避免沉没成本驱动。

## 7. 跨轮次、长工程的防失控规则

- 默认同一时间只推进一个主要学习能力；旁支记录入账，不顺手扩建多个系统。
- 决策、研究证据和实现版本用 ID 关联。每批写一个简短反证复盘：什么没预料到，什么被否决，下批如何避免。
- 保留已拒绝设计及理由，避免下一轮换个名字重新开发同一问题。
- 不重复拍未变化页面或重跑无关测试；版本、行为或风险变化才刷新相关证据。
- 不把用户数量、效果或预算凭空写成确定值；待估项必须有获取方式与下一责任动作。
- 用户中途反馈纳入当前批次；除非明确取消，不丢掉原目标。边界变化先更新批次卡及验证条件，再继续。
- 长期观察只能在用户授权后安排；当前不创建提醒、定时自动化、后台任务或新任务；本工程已启动，常规阶段推进无需重复确认。


## 8. 一次启动后的自动闭环调度

这里的“自动化”是代理在一次授权内主动执行并核验整个工作循环，不是只输出清单让用户逐步催办。2026-09-16 已收到启动指令，以下规则现已启用。

### 状态与选取下一步

账本记录运行状态：待启动 / 执行中 / 外部依赖等待 / 当前范围完成。每个批次按以下状态推进：

`候选 → 联网取证 → 价值判断 → 整合设计 → 原型核验 → 实施 → 验证 → 修复或缩减 → 再验证 → 提交与复盘 → 选择下一批`

- 价值不成立：记录否决依据，转下一个候选；证据不足：回到取证，不强行实施。
- 原型或测试失败：返回对应设计/实现节点；修复后重新核验受影响路径。
- 核验通过：做聚焦提交，更新账本和依赖，立即选取下一项可执行工作；阶段报告和提交不是等待用户说“继续”的理由。
- 下一步优先级：数据安全/崩溃/错误学习内容 → 核心路径与统计正确性 → 当前批次其他缺陷 → 证据缺口 → 新能力。优先解阻与修复，不在不稳定基础上扩张。
- 同时只保留一个主要实施批次；另列等待跨日效果或外部访问的观察项，不因它们阻塞所有独立研究。

### 每轮必须写回的最小状态

运行范围、当前节点、研究/机会/批次 ID、最新提交、通过与失败的检查、未决问题及严重度、成本/复杂度变化、外部等待条件、下一项明确动作。每个未决问题有 ID、受影响范围、解决或复核条件、所属批次，不能只写“以后优化”。

恢复时先核对仓库真实状态和记录的结果；中断中的操作先确认是否已完成，避免重复迁移、部署、计费或提交。上下文切换后从检查点续接，不重新开展已完成的研究。

### 防止错误与累赘累积

- 数据丢失、计数错误、错误教学内容、关键路径不可用等问题阻止相关功能扩展或发布；先修复或关闭该实验入口，保留用户数据。
- 每轮核对新增和关闭的问题，以及重复入口、废弃分支、临时开关、依赖、AI 调用、存储与维护负担。新增复杂度必须对应明确学习价值；不能只新增不清理。
- 非阻断问题也须有复核期限（下个相关批次或明确日期）；到期先处置再扩展该能力。连续两轮问题存量上升或已有预算超标，下一轮转为稳定与精简，直到恢复预算且不再净积压。
- 每完成一个主要能力，核验完整用户路径及受影响的聊天/收藏/账户路径，寻找重复系统和可删除的试验实现；清理须保留兼容性与历史数据。
- 自动化检查承接链接、构建、测试、幂等、统计不变量与预算比较；视觉、教学内容和产品取舍仍需证据审查，不能用“脚本通过”替代。
- 每轮允许“减少一个设计”成为有效成果。已否决项只有新证据出现才重新进入，防止反复重做。

### 持续推进与诚实停止

一次启动后，持续到当前约定范围完成、用户暂停、或所有有价值的可执行路径都被真实外部条件阻塞。单个产品不能登录、单个候选失败或一次提交完成，不构成整项停止理由。长期学习效果未到观察日期时，继续独立工作，保留待验证状态，不能伪造效果或无限等待。

确需额外付费、联系他人或缺少必要访问时，只提出具体缺口，并继续其他独立工作。自动选项不能替代所需授权。初始范围按总方案 P0–P5 的研究覆盖与合格候选队列执行；新发现先入队、过价值门槛，不无限扩大“必须完成”的范围。收束时列清已完成、否决、待观察和阻塞项目。

不能承诺进程退出或工具不可用后仍在后台运行。会话执行期间自主循环；发生运行环境中断则保存检查点，在恢复执行时续接。定时唤醒、跨会话自动恢复需要另行启用相应机制，当前不创建自动化。最终交付区分工程完成、试用验证和长期效果证实，不把未到期的研究混为完成。


## 9. 工作流运行监测与自我修订

在产品改进循环之外，加入工作流改进循环：**采集运行证据 → 识别流程问题 → 判断根因 → 提出最小规则变更 → 验证 → 发布生效版本 → 核对实际采用 → 后测或回退**。启动工程后，在原授权范围内主动执行这些修订，不需要用户逐次要求优化流程；不能自行扩大权限、削弱用户要求或宣称未经验证的改进有效。

### 监测在哪里发生

- 每次阶段切换、检查失败、用户纠错、工具/环境异常、提交前及恢复执行时检查；每批结束做一次汇总。监测依托当前运行事件，不创建后台轮询或无意义的定时检查。
- 从研究卡、检查输出、Git 差异和批次结果提取证据：漏检/重新打开的问题、重复失败、返工原因、缺失来源、重复劳动、等待原因、过时规则使用、测试误报、成本与未决问题趋势。
- 区分产品缺陷、规则缺失、规则互相矛盾、规则未执行以及环境故障。规则已经合理但未执行时先纠正执行，不机械增加清单；环境故障不能自动归咎于工作流。
- 数字附带分母、观察窗口与样本数。没有可比基线时记录案例，不凭一次顺利执行宣称效率提升。日志只保存必要摘要和证据引用，不复制凭证或私人聊天。

### 什么时候触发修订

关键漏检、用户指出流程性不足、违反硬性要求、规则冲突或使用过期版本，立即登记并暂停受影响的状态推进；其他独立工作可继续。同类返工连续两批出现、检查长期只产生噪声或记录负担明显超过价值时，触发流程审查。批末无异常也进行简短反证检查：有没有形式上通过、实际却未满足用户目标的步骤？

每次形成 `W-000` 修订卡，写明：触发事件与证据、受影响批次、根因与不确定性、原规则、最小变更、预期改善、可能副作用、验证案例、失败/回退条件、候选与正式版本、采用记录、后测结论。只修一个可归因的问题组，避免同时重写整个工作流。

### 如何验证和发布

1. 用触发问题回放候选规则，确认能够发现或阻止原错误；再检查正常路径及一个相邻边界场景，避免修复引入新的死循环、误阻断或重复工作。
2. 低风险文档澄清经一致性核对即可生效；会改变调度、验收或自动执行方式的修订，先在一个可逆批次试行，标记候选版本，并保留当前正式版本。用户硬性要求立即遵守，验证的是落实方法，不能以试验为由延迟遵守。
3. 核对总方案、工作流、模板和账本的引用与停止条件一致，检查未放宽权威取证、数据保护、学习验证或授权边界。不能通过降低标准让失败“通过”。
4. 将通过验证的修订做聚焦提交，更新版本账本中的唯一生效版本、变更理由、证据和迁移要求。未经验证的新草案不能自动覆盖正式版本；版本号更大不等于更完善。
5. 下一批启动、恢复执行和关键阶段切换时核对生效版本，并在批次卡写入实际采用版本。进行中批次在安全检查点迁移；紧急纠错立即阻断受影响动作，非紧急变更不改变正在运行的写入操作。
6. 默认在随后两个适用批次复核：同类错误是否再现、检查是否执行、返工/时间/成本是否增加，以及是否引入遗漏。样本不足继续标记待观察。若变差，回退到上一已验证规则或提交修正版，记录原因，不删除历史证据。

### 避免“优化流程”本身成为累赘

优先删除无效、重复和已过时的规则，再考虑新增步骤；每条强制检查必须对应具体风险或失败证据。每批仅做简短监测摘要，详细修订卡只用于实质问题。严重问题优先处理；其他流程优化不无限挤占产品任务。不得以自我优化为由无休止重写计划。

执行结果分开标注“规则已发布”“批次已采用”“改善已观察到”。当前建立的是监测与改进制度，尚无实际运行样本；不能保证永远最优，但必须保证采用最新通过验证并正式生效的版本，保留对其纠错与回退的能力。
