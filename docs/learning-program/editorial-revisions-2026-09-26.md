# 生成候选修订与重新审题

该流程用于修复有价值但未通过审核的生成候选。修改题干、提示或解析后必须生成新的待审任务；不能修改旧任务的通过标记、重新设置尝试次数或复用旧审题报告。已发布内容不走这个入口。

## 操作合同

`pnpm learning:generation inspect 任务UUID` 查看原稿、失败原因、每次审题及关联修订。`revise 修订JSON文件` 接受：`requestId`（新 UUID）、`sourceJobId`、`candidateHash`、`editor`、`notes`（30 至 1000 字符）、`unit`（完整修订稿）。角色、水平、版本和原稿身份必须一致；服务端为修订任务生成新单元 ID，并登记生成后编辑的作者来源。

请求 ID 和输入绑定，重复请求返回同一修订任务。一个原稿哈希只允许一个后继修订，后续修改继续接在新稿之后。原稿和运行记录不改写；修订表保存提交内容、哈希、编辑者与说明。当前蓝图变化会阻止旧修订直接复审。

Worker 领取修订任务时使用原有每日预算、租约和三次重试上限，只执行新的独立审题请求，不伪造作者模型调用或费用。审题输入不带作者答案或解析，逐题 Schema 明确选项、词块和配对 ID。自动检查仍会核对独立解答、错误反例、题型比例、重复内容、角色、难度和引用合同。

复审通过后进入 `review`，仍不能被用户抽取。编辑者逐题核查内容和解析后，用现有 `publish 审核JSON文件` 对当前候选哈希发布。审核不能由编辑接口跳过。

## 工程验证

22 项学习单元测试、12 项隔离 PostgreSQL 测试（生成、修订及鉴权接口），类型、改动文件 ESLint、架构检查通过。隔离数据库证据：`build/learning-engine-db-1790402313/result.json`。修订事务验证了并发幂等、哈希冲突、原稿和失败审计保留、统一预算、盲审单次调用、复审拒绝、蓝图漂移及禁止直接改写已发布单元。

工程夹具只证明流程约束，不能证明真实候选的语言质量。真实修订与发布结果另行追加。
