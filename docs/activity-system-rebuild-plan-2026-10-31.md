# 城市地点与固定相遇系统重构施工方案

日期：2026-10-31。范围：活动入口、城市地点、公共 NPC 设定、相遇与重逢内容、素材、兼容迁移及验收。

用户只选择去哪里。系统从这个地点内符合条件的人物中安排一次有来由的相遇；人物为什么在场、双方为什么接触、接下来发生什么，由与地点绑定的预写故事负责。每个人有稳定的国籍、成长地、当前城市和唯一首次相遇地点。城市的人物数量适度有别，地点与照片也体现当地生活。

这是施工设计，本次不发布运行代码、重写现有角色或导入新内容。用户已于 2026-10-31 确定每城 3—5 个地点、保留少量独处与相遇保底、重分现有 200 人，以及保留角色身份与旧经历并明确迁移新设定。第 2 节记录已确定规则；具体选址、概率数值和内容制作参数按下述方案实施及校准。

## 2 已确定的产品规则与实施参数

### 用户已经明确的规则

1. 去掉“问问路线”“喝口咖啡”等入口级动作，只选择目的地。
2. 国籍和当前城市是稳定设定，在其他城市不能随机遇到此人。
3. 大多数人物应在所在城市成长；其余人物有明确的迁居、求学、工作或旅行原因。
4. 每人一条固定首次相遇故事，硬绑定一个当地地点；不在其他地点触发。
5. 城市地点组合各有特点，并配对应场景的照片。
6. 伦敦、纽约等知名城市人物较多，城市间差距受控。

### 用户已答复的产品取舍

| 决策 | 用户确定的方向 | 对施工的影响 |
| --- | --- | --- |
| 每城地点数 | 每城 3—5 个，由城市特色决定；本方案配置共 54 个 | 每处至少 3 人；类别可重复，组合、空间、人物和故事因城市而异 |
| 是否允许独处 | 保留少量独处，并设置相遇保底 | 需要服务端保底状态和单独的独处内容；建议连续两次独处后第三次遇人，前提是当地有合格人物 |
| 人物总量 | 重做现有 200 人的城市与地点分配 | 所有现有 NPC 均有新归属；不以新建身份替代旧人，不自行增加人数 |
| 老角色处理 | 保留角色身份与旧经历，明确迁移新设定 | 保留稳定 ID、旅伴号、头像、关系和历史；国籍、当前城市等修订通过设定版本记录 |

上述四项已确定，无需重复确认。第 7 节的 85% 相遇率、75% 新人物优先率和具体保底阈值是初始调参值，不写成用户指定的数值。

### 建议补充的规则

“在伦敦成长”与“英国国籍”分开记录。伦敦本地人可以有不同族裔和家庭背景；出生在外地、从小在伦敦成长也可以算本地成长。首版每城约 70%—85% 采用本地成长设定，其余有具体在城原因。该比例是创作目标，不是城市真实人口统计，也不据此推断头像外貌、口音或人格。

场景使用有证据的同城实拍作为发布要求。选不到合适照片时先换同城选址，不拿异地街景冒充，也不把 AI 图标成实拍。照片是故事的空间依据，因此首次相遇不能套用赴约原型里“任意同城氛围图轮播”的规则。

“自由发挥”安排在离线内容创作阶段：故事可以包含买东西、避雨、等待、帮助、聊天等行为；正式运行仍读取审核通过的固定故事。用户在故事节点决定怎样回应；进入咖啡馆并不代表已同意替陌生人付钱、跑腿或交换联系方式。

首次相遇与重逢都留在该人物绑定的地点。老朋友可以继续远程聊天，未来赴约另走赴约系统，不把固定相遇地点扩展成好友只能在那里出现的世界规则。首版不做 NPC 迁城日程、GPS 定位或按真实营业时间关闭入口。

## 4 人物设定与首次相遇的创作标准

### 人物资料

沿用稳定的 `npcId`、旅伴号、头像和核心个性；补齐规范化的 `nationalityCountryCodes`、供展示的 `nationalityLabel`、真实 `hometown`、成长地描述、`localConnection`、`currentCityId`、`presenceReason` 和 `firstMeetingPlaceId`。`localConnection` 取 `grew_up_here`、`settled_here`、`temporary_stay`，不从国籍字段自动推导。

每人必须回答：平时如何在这座城生活、为何来到此处、眼下想做什么。原因可以很普通，不要求每个人都有重大创伤、奇怪职业或神秘物件。例如“住在附近，每周来买菜”比“靠绳结记住失效约定而在公园迷路”更容易建立自然的场景联系。

一座城内的职业、年龄、兴趣、话语节奏和社交方式保持差异。多数相遇围绕生活小事展开；帮助、分歧、巧合可以出现，但不把所有人物写成求助者、导游或人生导师。

### 每条故事先写因果卡再写正文

| 因果卡字段 | 必须回答的问题 |
| --- | --- |
| 在场原因 | 此人为什么此刻在这个地点？与设定是否一致？ |
| 共同现场 | 用户和此人共同能看见、听见或接触到什么？ |
| 接触触发 | 为什么恰好向用户开口，而非突然向陌生人倾诉一生？ |
| 眼前目标 | 双方接下来几分钟能完成或讨论什么？ |
| 两次选择 | 两种回应如何带来不同、可见的后续？有没有自然保留距离的路径？ |
| 收尾 | 小事如何结束？认识了对方什么？为什么可能愿意下次再聊？ |
| 场景依赖 | 如果把背景换成另一类地点，故事哪个关键动作会不成立？ |
| 可见与不可见物件 | 照片可见物件如何使用；需要的额外物件由谁带来，正文何时交代？ |
| 重逢前提 | 只引用所有首次分支都成立的事实，或明确声明所需实际分支 |

保留七节点树作为首版结构：开场 `start` 两个选择，进入 `a` 或 `b`，再各选一次进入四个结尾。每节点 4—6 段双语旁白/对白，选择不能只是同一句话换措辞。正文在用户做决定之前停下，所有分支都校验物件、空间、动机和承接。

每人首版另写一段短重逢，共 200 段。已认识人物不重复自我介绍；不要根据未走过的首次分支声称“你上次买了那本书”。通用重逢只引用共同成立的事实。未来增加有前提的多条重逢，不用无限次重演初见补充内容。

### 伦敦咖啡馆样板

以下 Alex 是说明规则的新样板，不代表当前库已存在或已改名的角色。

Alex 在伦敦长大，在附近工作，午休时常来咖啡馆看书。店员刚把一叠街区读书会传单放到取餐台，Alex 手里有其中一本书，正在核对传单上的版本。用户在同一处等待取餐，Alex 指着传单问一句：“你也在看这个活动吗？我不确定他们读的是这版。”

用户可以聊书，也可以只帮忙读一眼传单。前者进入“为什么会选这本书”，后者进入“看清日期后聊附近活动”；第二次选择可以继续交换看法，也可以准备离开。收尾时只建立一次短暂认识，添加好友仍由用户决定。

空间要求：照片能支持咖啡馆及等待取餐的处境；书属于 Alex，传单由店员刚放下，不能凭照片上不存在的固定公告栏推动情节。如果照片不支持取餐台，则修改开场动线或另选照片，不要求画面凭空配合正文。初见故事固定在咖啡馆，在河岸或市场不会抽中 Alex。

### 内罗毕市场样板

一位在内罗毕成长、每周替家里买菜的人，带着旧布袋在菜摊前挑选。用户也在等摊主称重，一把刚放下的香草留在两人之间，双方从“这是谁挑的”确认物品归属，再自然聊到各自喜欢怎么做饭。可继续聊，也可把香草递回后道别。不要为了突出异国特色，让当地人物主动表演文化课或替用户决定买什么。

剧情审核采用“通过／返修／拒绝”，结构校验之后必须逐条看因果卡和四条完整路径。AI 可以协助起草、查矛盾，但不能以一段自评替代最终编辑审核。

## 5 照片与呈现方式

首版为 54 个地点各准备一张正式主图、一份来源记录和一个裁切配置。选择界面、进入后的场景与故事阅读使用同一地点媒体族，不能进入市场后退回通用咖啡馆。静态图先完成真实感和原生验收；视频、物体锚点、复杂透视和轮播不作为首版依赖。

来源记录至少包含城市、地点、作者、来源页、原始文件、许可及版本、商业使用与修改条件、署名要求、原始/输出哈希、像素尺寸、城市归属证据、实拍标识、处理记录及验收状态。地点坐标可记录到内部来源证据中，但不要求用户开启定位。

验收逐项覆盖：确为该城、确为该类地点、视角和动线合理、故事所需空间存在、标准屏与小屏裁切、大字与文字对比度、入口命中区及返回。按照[现有视觉规范](activity-scene-visual-acceptance.md)保存每版记录；待证实和拒收素材不能进入正式发布清单。

少数照片暂缺时，该地点保持制作中，不用其他城市图片补位。线上已发布素材加载失败时使用同一地点的已缓存缩略图；仍不可用时显示明确的加载失败和重试，不能无提示地替换城市或改变选人结果。

照片中有晴天、室内外、市场摊位等明确事实时，剧情不得随意改成暴雨、夜晚或另一类空间。照片不证明 NPC 真在照片里，人物对白继续以头像标识。首版不制作真人照片与 NPC 的视觉合成。

## 6 数据契约与模块职责

### 同一发布版本的内容清单

新增 `Content/ActivityWorld/<release>/` 作为内容源，保存 `places.json`、`characters.json`、`encounters.json`、`media.json`、`migration-map.json` 与编辑验收记录。编译器输出 App 与后端共同使用的不可变清单，禁止两端各维护一份手写配额表。运行资源放入各自现有资源机制，源照片与证据按现有 Assets 约定保存。

| 对象 | 核心字段与不变量 |
| --- | --- |
| 发布清单 | `schemaVersion`、`releaseId`、`manifestHash`、依赖版本与最小客户端能力；一经发布不可原地改写 |
| 地点 | `placeId`、`cityId`、类别、显示名称、街区、副标题、`mediaId`、允许的空间事实、独处内容引用；同一 ID 的城市不变 |
| 人物设定 | `npcId`、`canonVersion`、国籍、成长地、`localConnection`、`currentCityId`、在城原因；基础身份与设定版本分别管理 |
| 相遇绑定 | `releaseId`、`npcId`、`placeId`、首次故事与重逢引用；同一发布内每人恰有一个首次相遇绑定 |
| 故事 | `storyId`、`storyVersion`、`npcId`、`cityId`、`placeId`、因果卡、七节点、重逢前提；引用全部存在且同城 |
| 媒体 | `mediaId`、本地资源或受控远程位置、城市/地点证据、尺寸、哈希、署名、裁切和验收状态 |
| 外出会话 | 账号、`runId`、发布/人物/故事/媒体版本、城市、地点、分配结果、已读位置、选择路径、修订号、状态与时间 |

已有 `card.regionId` 在旧协议里继续存在。新协议以设定版本的 `currentCityId` 为活动城市，客户端适配层投影为需要的旧字段；禁止长期维护两个可以独立修改的城市值。规范国籍可以用一个或多个国家码，苏格兰、威尔士等身份另外保留显示描述，避免错误简化人物的文化身份。

### 服务端存储与边界

新增版本化地点目录、人物设定版本、相遇绑定和会话进度表。表名在实现中与项目命名统一；必需约束包括发布内 NPC 首遇绑定唯一、地点与故事同城、版本引用不可缺失、账号与 `runId` 唯一、选择推进修订号匹配。当前 `npc_scene_affinities` 的主键没有版本，不能直接用来完整并存相同绑定的多个库。

保留 `public_npcs` 的稳定身份和旧人物卡快照，不静默覆盖旧卡；新设定放进版本表。旧选择器继续读取旧卡和旧关联，新选择器只读取所请求发布中的设定和绑定。头像、旅伴号和已有关系不因新发布更换或解绑。

`routes` 做认证与输入校验，`service` 做外出规则与跨模块协作，`repository` 持有事务和锁。当前城市由 domain 模块公开的服务/类型提供，在 `server.ts` 装配；不要从 NPC 模块导入 domain 仓库。位置校验与分配需要共享事务上下文，对同一用户资料行使用与旅行一致的行锁，避免读取城市后发生并发旅行再提交异城相遇。共享事务类型留在基础设施层，锁顺序统一为用户位置行在前、NPC 会话相关锁在后。

iOS 的地点和故事模型放在 DomainKit，共享 HTTP DTO 放 BackendKit。持久实体留在 PersistenceKit actor 内，跨 actor 和 UI 只传 `Sendable` DTO。HomeFeature 负责地点浏览和阅读交互，App 继续装配导航、聊天入口和会话生命周期；不让 Feature 相互导入。

## 7 分配与恢复的执行规则

### 新外出的请求与返回

建议增加 `POST /v2/outings`，输入 `runId`、`placeId`、`releaseId`。城市从地点目录推出，再与服务端当前城市核验，不能由客户端任意声明。响应为稳定的 `runId`、城市/地点/版本快照及 `encounter` 或 `solitude`；相遇同时返回 NPC、故事引用和首次/重逢模式。保留旧 `/v1/npcs/authored-encounters` 支持旧版客户端。

服务端依次执行认证与游客权限、同账号同 `runId` 查询、发布与地点校验、当前位置锁定及核验、候选筛选、概率与保底、原子保存分配。已存在且请求哈希一致的会话原样返回；不同参数复用同 `runId` 返回冲突。插入前在锁内重查相同 `runId`，由唯一约束兜底，不能让两个初始请求各保存一次结果。恢复旧会话先读已保存快照，不因用户后来旅行而重新选人。

候选必须同时满足：属于该发布、设定城市等于地点城市、唯一首遇地点等于请求地点、故事/媒体准备完成、人物可用、未被用户移除、语言符合要求、头像兼容约束满足。候选不足不能放宽城市或地点，也不能现场生成一个新 NPC。

### 建议的概率和保底

有候选时相遇概率为 85%；连续两个被用户实际看见的独处结果后，下一次必遇人。未遇到人物的原因分别记录为正常独处、无可用候选和技术失败；技术失败绝不计为独处或消耗保底。

有尚未认识的候选时，相遇内 75% 选择新人物；连续两次实际展示熟人后，下次相遇强制从新人物中选。新人物内部均匀抽取，熟人内部沿用有下限的近期权重。没有新人物时正常重逢，地点可给出轻量提示“这里的人，你都见过了”，不显示身份剧透或虚假的还剩人数。

保底按账号和城市计算，候选始终限于本次所选地点。因此保底只在此地点还有相应合格人物时生效；如果此地点全认识了，不能为了兑现“新人物”从其他地点借人。跨地点保底保留至用户选择有新人物的地点。

重逢、独处和候选枯竭都需要可读内容。每个地点至少两段无人物的短观察，轮换后才允许复用。枯竭时可以建议换地点，但不自动跳转，不把已移除的人重新塞进来。

### 分配与认识分开提交

分配时保存结果和随机抽取依据，但不直接判定认识。同账号同时最多一个可继续的外出会话，由资料行锁和会话唯一约束共同保证；另一设备请求新外出时返回现有会话引用，不能把新参数伪装成原请求。用户可继续或明确结束这次外出；未被看见的结果不推进关系或保底。已下载的故事不因设备离线一段时间而自动过期。

客户端展示完整开场节点后幂等确认 `opening_presented`，才更新相遇历史、联系人 candidate 状态和相遇保底。确认失败允许继续本地阅读、暂存选择并排队重试；同步队列先补确认，再依序提交选择和完成。独处展示确认更新独处计数。选择推进和完成分别保存，完成不自动加好友或结算额外好感。

推荐状态为 `reserved → opening_presented → in_progress → completed`，另外允许用户明确触发 `abandoned`。应用后台和普通返回只暂停，不标为主动放弃。用户另开一次外出前先提供继续或结束当前外出的明确操作，避免无意占用预留。若另一设备已结束该会话，本机待同步选择保留为本地草稿并显示冲突，不复活已结束的正式会话。

新增 `GET /v2/outings/:runId` 恢复、`POST /v2/outings/:runId/presented` 确认展示、`POST /v2/outings/:runId/choices` 提交 `expectedRevision` 与稳定选择 ID，以及 `POST /v2/outings/:runId/complete` 完成。接口只接收选择 ID，不接收客户端提交的故事正文或任意跳转目标。并发版本冲突返回已保存状态，不重复推进。

发布清单随 App 提供完整正文；服务端保存对应不可变清单用于校验故事节点。新会话需要联网，已分配且资源完整的会话允许离线阅读与本机暂存选择，按顺序补传；离线时已认识与加好友等权威写入显示待同步。恢复响应带实际版本；客户端缺少该版本时提示获取内容或更新，不能拿最新版故事继续旧分支。

## 8 原生页面改造

活动页以当前城市为上下文，主问题是“今天想去哪里”。按该城目录显示 3—5 个当地地点及各自实拍，点击地点直接开始或恢复外出。采用支持纵向滚动的照片卡列表，五处地点不挤成同屏五个小按钮，三处地点也不强行补空卡。具体卡片比例先用三城样板检查；不再依赖照片里某个杯子、纸巾或地图作为入口。

进入后显示地点照片和准备状态，结果就绪即可阅读。建议移除当前固定 15 秒等待及十五城串剪作为每次相遇的强制流程；过渡可以短暂保留，但不能阻止已准备好的故事开始。旧过渡影像的已有验收记录继续保留。

故事沿用已有英语阅读、中文对照、查词、语音、历史与选择交互。初见、重逢和独处各有清晰的结束状态；添加好友与返回聊天复用现有权限、好友位和同步逻辑。故事内没有交易成功或加好友的默认承诺。

“相遇与足迹”记录城市、地点、照片版本、人物、实际分支和正文快照。旧记录继续按原样展示，不要求把旧 `park-seat` 反查成新咖啡馆。只读历史与继续中的正式会话分开，回看不再写入相遇次数。

切换城市时已开始的故事保留原城市、原地点和原版本；阅读结束后新外出使用新的当前位置。游客沿用起始城市限制，游客认领账号时合并会话与保底记录并去重。教学和免登录预览采用隔离样板，不写正式账号或污染真实人物池。

## 9 老角色与旧版客户端的迁移

### 身份变更清单

这里的“保留身份与旧经历，迁移新设定”指保留老朋友和聊天，更新角色资料与相遇规则。稳定身份主要是同一个 NPC ID、名字、旅伴号、头像，以及此人与用户的关系；国籍、成长地、当前城市和相遇地点可以按本次重构修订。后台记录修订前后资料，不要求用户逐个角色确认或理解版本号。

例如老用户曾在伦敦公园认识 Alex，新版将 Alex 绑定到伦敦咖啡馆：原联系人、聊天、关系和公园初见记录保留；以后只有在指定咖啡馆活动才能随机遇见他，老用户走重逢，未认识他的用户走新版初见。旧经历不会被改写成“你一直是在咖啡馆认识他的”。

对现有 200 人逐个标记“保留城市与身份”“修正明显虚构资料”“需要迁城”“需要改写相遇内容”，列出前后资料及受影响故事、聊天提示、时区和语音选取；同一人可有多项修改。全部 200 人均应在新库有唯一归属，不能通过删除、换 ID 或另建人物凑数量。资料可以修订，但不能连带篡改用户实际读过的故事和旧聊天。

采用用户已确定的稳定身份加设定版本策略：已有关系、头像、旅伴号、消息、记忆和历史正文不变；旧设定作为历史保留。资料修订随新版统一迁移，对已认识角色提供一次可查看的更新说明，不设置逐人确认流程。合理的现居城市调整可以采用搬迁背景；国籍、成长地等编辑纠错直接标为资料修订，不编造一次从未发生的入籍或成长经历。更新后正式相遇仍固定在一个城市，不做随机流动。

第 3 节的精确配额与本地成长比例需要一起核验。只把外地角色迁入伦敦，不能增加“在伦敦成长”的人数；需要调整成长地时明确列为资料修订。逐人审校后，在现有 200 人内优化城市分配和设定，保留旧值与旧经历。精确配额或 70%—85% 的建议比例若无法同时满足，应优先保证多数本地成长与人物一致性，再微调人数和比例，不自行增人或篡改历史。

已开始故事锁定旧设定；已有聊天不能在同一轮切换人设。客户端在下一段新会话采用已迁移的设定版本，并把系统资料修订与用户共同经历分开，不把“编辑修正国籍”写成 NPC 声称亲历的事件。影响事实记忆的冲突保留来源与旧值，不删除用户编辑过的记忆。

迁移校验按现有库的 200 个 `npcId` 逐个对账，新旧集合必须一致，旅伴号和头像绑定也必须一致。人物资料修订与首次故事换版不产生第二个人物实体。已认识此人的用户进入重逢，不因新版故事未读过而再次执行初见。

### 发布和回退

1. 增加新表与新协议；保留旧表、旧资料和 `/v1` 行为。迁移编号根据落地时 journal 最新值生成，本方案不预占迁移号。
2. 新导入器先验证不可变清单，在事务中只写新 `releaseId` 的目录、设定和绑定；不全表删除 `npc_scene_affinities`，不释放已绑定头像。
3. 分配器根据客户端支持版本与请求发布读取对应池；新 App 打包匹配正文与媒体，旧 App 继续请求 v3。人物城市等设定从各自版本读取。
4. 三城样板先在隔离环境完整验证，再以显式测试账号启用新版本；不使其他十二城出现制作中空页。正式全量发布需完成十五城整包。
5. 部署后端与资源，再验证对应版本的在线目录、严格筛选、重试和资料兼容；iOS 发布独立安排。后端部署遵循仓库既有授权，不另外要求重复批准。
6. 激活指针可以退回，已有新会话继续使用保留的版本快照；数据库保持向后兼容，不删表回滚，不删除人物或用户数据。

后端重点更新现有 `test/unit/authored-library.test.ts`、`test/integration/npc-authored.test.ts` 与 `npc-encounters.test.ts`，新增外出会话/版本迁移集成用例。纯函数用定向 Vitest，接口/类型变更加 typecheck，跨模块变更加 architecture；数据库验证使用隔离环境。不要运行会清库的生产测试。

iOS 按改动选择 `ActivityJourneyTests`、`ActivityEncounterChanceTests`、`SocialEncounterDiversityTests`、`EncounterServiceTests` 以及新增内容加载和进度恢复套件，使用 `Scripts/test.sh -only-testing:LingoTripTests/<Suite>`。现有断言“三景九动作”必须替换为城市目录与版本约束，不只删除失败断言。UI 先复用当前模拟器短程核验，完成代码改动后按 `docs/development.md` 使用 `Scripts/preview.sh` 安装并留下最新构建。

上线后用测试账号检查三类城市：新相遇、重逢、一次独处/保底、相同会话重试、切城与旧版调用。监测空池率、失败率、首次故事重复展示、遇新人间隔和按地点的内容覆盖；正常独处不算系统失败。三城样板的体验观察用于调概率，不以随机短样本宣称所有人可达；可达性由全清单确定性检查证明。

## 12 首版范围与主要成本

主要内容工作量为现有 200 人各一条首次故事，每条七节点、四结尾；另有 200 段短重逢、108 段独处和 54 张已验收同城照片。首次正文共 1,400 个节点，不能把两百条一句话梗概算成两百条可发布剧情。现有素材只有在身份、城市、地点和每条分支审核都通过后才能复用。

首版重点完成地点化选择、人物地理一致、固定剧情与照片强绑定、恢复和版本迁移。赴约的自由输入、实时生成、记忆提炼与关系结算沿用[独立赴约方案](appointment-story-design-2026-10-30.md)，不混进随机初见重构；可共享城市资料、媒体来源和阅读组件，但不能共享放宽场景绑定的规则。

四项产品取舍已确定，下一施工步骤是落实目录契约与逐人迁移映射，再完成三城样板，验证“为什么在这里遇到这个人、为什么会发生这件事”。样板通过后按同一契约扩展内容，避免先批量生成两百篇，再发现整套逻辑需要推翻。
