## 已落实的保护

- 发布、正式目录导入、公共题库导入共用`maintenance.sh`，锁覆盖执行和稳定观察；固定systemd单元名继续防止终端断开后的重复维护。普通生产SSH直接运行题库CLI会在加载内容前拒绝，不能靠环境开关绕过。该约束不是防止root故意修改系统的安全边界。
- 维护前要求readiness正常、可用内存至少384MiB、磁盘剩余至少512MiB，且没有持续内存/I/O压力。实际执行限制256MiB内存、128MiB Node堆、禁用维护单元swap、50%单核CPU、磁盘读写各2,000,000字节/秒、10分钟时限；不在线编译、不临时安装缺失依赖、不自动删除回滚目录。
- 维护结束允许自身限速产生的短暂压力消退，三分钟内须取得连续一分钟稳定。连续三次健康失败会停止观察。发布只有通过观察才清除回滚事务；失败、超时或OOM由退出钩子恢复旧程序指向和版本环境，数据库不自动回退，恢复后仍需健康确认。
- 正式目录逐文件验证媒体，不再把全量媒体Buffer保留到上传结束；上传前重新读取并复核，防止校验后文件变更。内容哈希、审核绑定、判题样例和事务原子性均保持。CLI新增阶段耗时和RSS记录。
- 两类题库写事务均限制锁等待5秒、单语句30秒、事务空闲30秒，避免无界等待占用连接。
- 每分钟记录主机资源、进程RSS和CPU/磁盘增量；仅记录进程名，不采集参数、环境变量、凭证或业务内容。日志每份4MiB、最多6份轮转备份，采样服务自身限制48MiB、10%CPU和10秒运行时间；不会自动重启业务。

## 仍存在的边界

本次修复的是已确认的维护预算缺失、入口可绕过、内存重复保留、无界等待和现场证据不足。仍不能确定旧故障的唯一触发进程，也不能在缺少云侧历史指标时认定是云盘还是实例性能上限。

这台机器标称2GiB、系统实际可见约1613MiB，同时运行数据库、缓存、对象存储、API和Worker，容量余量仍有限。维护上限不等于业务峰值容量保证；没有通过加大配额或修改swappiness、crashkernel来掩盖压力。后续应结合新增采样和云侧分钟级指标决定扩容或服务拆分。

服务器分钟级留档独立运行。Codex原有五分钟心跳任务保持此前暂停状态，仅更新了当前版本与监测说明，没有擅自恢复任务。
