# 2026-10-07 生产故障调查

本轮按用户要求进行只读调查，没有部署、重启、安装依赖、修改内核参数或在生产复现负载。结论基于服务器历史采样、日志、发布代码、用户提供的云诊断截图以及恢复记录。

## 结论与置信度

**已证实的是主机级严重资源阻塞，同时出现云盘I/O受限和内存压力；精确触发进程尚未定案。** 最有证据支持的解释是：低内存余量的主机连续进行两次服务切换，紧接全量目录发布，放大内存回收及磁盘访问争用，最终业务、数据库维护、日志与SSH共同失去及时响应。内存压力与云盘限流谁先触发、是否有第三方进程参与，现有数据无法确定。

不能把此次事故写成已经证实的“线上编译OOM”“数据库大事务写爆磁盘”或“云盘硬件损坏”。没有找到对应的OOM杀进程、文件系统错误或块设备I/O错误记录；故障窗口内日志不完整，缺少记录也不等于绝对没有发生。

运维流程存在明确不足：在没有主机级资源预算和稳定观察的情况下，仅凭一次readiness成功即连续切换、启动全量导入。回滚兼容版本有必要保留，但不应因此压缩观察窗口。这项流程风险由本次发布操作承担，不能简单归咎于云厂商或服务器规格。

## 容量、配置与代码证据

- 实例元数据确认规格为`ecs.e-c1m1.large`、地域深圳。阿里云当前规格表为2vCPU/2GiB；系统可见内存约1613MiB。当前启动明确预留256MiB crashkernel，其余内核和平台保留继续占用空间。不能按标称2GiB全部分配给应用。
- API、Worker、MinIO的systemd `MemoryHigh`和`MemoryMax`均为infinity。当前观察到的各服务峰值不能相加当作事故瞬时用量，也不能用当前RSS倒推历史元凶。
- 按原CLI使用的环境文件启动同一Node运行时，默认V8堆上限902.5MiB，另有堆外内存。这个上限不是实际消耗，但说明单个维护进程缺少与约456MiB余量匹配的预算。
- 当前`vm.swappiness=0`来自`/etc/sysctl.d/99-apsara-sysctl.conf`，文件日期6月15日。内核文档说明0会推迟交换区介入，直到空闲和文件页低于相应区域高水位；不能说它完全禁用swap，也不能将2GiB swap视为等量及时可用的内存。故障瞬间swap用量没有采样，不能宣称已经发生交换风暴。
- `loadCuratedCatalog`会先加载并保留全量140段音频、44张图片，再读单元和审核记录；媒体原始字节约33.65MiB，**这本身不足以证明内存耗尽**。随后CLI先逐个核验/上传对象存储，最后才创建数据库连接并执行目录事务。缺少阶段日志，原CLI最终停在哪一步不可知。
- 发布包24MiB，构建在本机完成；两个原部署日志都没有依赖安装输出，依赖清单也没有变更。未发现事故窗口内远端编译或依赖安装证据。
- 旧发布脚本在readiness成功后还会自动清理旧目录。它也是不必要的集中I/O风险，但没有证据证明清理是此次唯一触发点。
- 恢复前只读核查确认新三个高中单元未提交；不能把未提交等同于事务一定未启动或一定在等待某条SQL。

规格来源：[阿里云共享型实例](https://help.aliyun.com/zh/ecs/user-guide/shared-instance-families)。参数语义：[Linux内核swappiness文档](https://kernel.org/doc/html/latest/admin-guide/sysctl/vm.html)。云盘有效性能受实例与云盘两层约束，当前规格表实例上限为8000 IOPS、0.4Gbit/s；尚未取得实际磁盘类型、性能等级及该时段利用率，不能认定碰到的是哪层上限。[阿里云存储I/O性能说明](https://www.alibabacloud.com/help/en/ecs/user-guide/storage-i-or-o-performance)

## 已做保护与仍需落实的措施

已完成的恢复措施见[重新上线记录](recovery-release-2026-10-07.md)：备份、串行维护、临时systemd资源限制、禁用维护进程swap、强制依赖缓存复用、默认不清理旧版本、保留回滚。受控条件下相同正式内容发布及线上验收成功，说明不必靠重置数据恢复；它不是无资源限制条件下的对照实验。

仍需落实，不能误报为已完成：

1. 将维护资源预算、余量预检、跨部署/导入的统一锁和稳定观察固化为唯一发布入口。此次systemd限制是恢复命令显式设置的，直接运行CLI仍可绕过。
2. 为目录发布增加阶段耗时/内存记录，并减少全量重复加载；保留哈希、逐题审核和事务保证。
3. 保存更细的系统及进程采样，至少覆盖发布前后；当前10分钟sysstat和5分钟健康检查无法定位几秒至几分钟的尖峰。要限定日志体积、保留期和采集成本。
4. 按服务峰值重新做容量预算。先核对实际磁盘限流来源，再决定内存扩容、服务分离或磁盘调整；不能仅凭此次截图盲目升级磁盘。
5. 若考虑调整swappiness或崩溃转储预留，需单独评估可靠性取舍和重启窗口；本轮未改变这些设置。
