# 聊天空回复与重复恢复修复

2026-09-11：用户截图中的“暂时没有收到回复”并非当前余额不足。已核实同一账号最近七次
GLM 聊天调用均无正文且输出计数为 120；最新一次供应商详情为 Relace，finish_reason=length，
native_tokens_completion=120、native_tokens_reasoning=122。以前的服务把这些调用记为成功。

客户端默认请求 120 输出 tokens；GLM 的总预算还包括思考，可能在正文开始前耗尽。
打开聊天页又会自动重发最后一条未答用户消息，且失败状态没有持久化，形成重复尝试。
电话转写也是用户消息，因此会进入同一恢复路径。

## 修复

- OpenRouter GLM 聊天使用 minimal 思考强度；总输出预算至少 512，仍受后台路由上限约束。
  服务端统一计算调度和计费估算的预算，旧客户端也生效；可见正文的简短要求不变。
  该模型强制思考，关闭思考的验证请求返回 400，故未采用关闭方案。
- 普通与流式调用没有正文时返回 AI_EMPTY_RESPONSE，不记录成功、不缓存空结果。
  实际用量保留到成本账本，该类调用由服务承担，不扣用户积分。
- 客户端将该错误映射为不自动重试的空响应错误。用户请求派发前保存中断标记，重新进入
  或重启后不再自动重发；显式“重试回复”可继续，新的用户消息仍正常触发回复。
  尚未派发的消息仍可自动恢复，已有转写和聊天内容保留。沿用现有中断字段，无模型迁移。
- 电话收到空流也明确报错，避免静默结束后被聊天页再次付费重发。
